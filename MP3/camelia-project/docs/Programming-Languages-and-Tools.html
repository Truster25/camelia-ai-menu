1. THE SHORT ANSWER

The system is written in two programming languages. The part the customer and the manager see is written in TypeScript, which is JavaScript with type-checking added. The part that holds the data, serves the request and runs the recommendation is written in Python. Everything else is a supporting tool rather than a programming language: a database, a styling framework and libraries.

In one sentence, for the paper
The system was implemented in TypeScript (JavaScript) on the client side and Python on the server side, with PostgreSQL as the database, giving a clear separation between the presentation layer and the application and intelligence layer.

Both languages were chosen deliberately. TypeScript is the language the React framework is written for, and it catches mistakes while the screens are being built. Python is the language of the machine-learning libraries, so the recommender and the web server can live in one program and be tested with the same tools.

3. WHY THESE LANGUAGES WERE CHOSEN

3.1 Why TypeScript on the client side

  • Fit with the framework. It is the language React is designed for, so the screens use the framework the way it is meant to be used.
  • Fewer faults reach the user. A misspelt field or a wrong data type is reported while the code is being written, instead of appearing as a blank screen during the demonstration.
  • Nothing to install. It compiles to plain JavaScript, so it runs in every modern browser with no installer for the customer.
  • One code base, every screen size. The same code base serves a phone, a tablet and a laptop screen, which matters for a restaurant where customers are seated.

3.2 Why Python on the server side

  • The intelligence and the server share one language. The recommender needs a text-similarity model and a ranking formula. Those live in Python libraries, so the model and the web server run in the same language and the same process.
  • The method stays explainable. The whole recommendation method can be read, changed and tested in one file, which is what makes it defensible in Chapter 5 of the paper.
  • It can be explained. Python is the language taught for data handling and machine learning, so the code can be explained to a marker who does not specialise in web development.

3.3 Why two languages rather than one

A single language was possible, but a poor fit. Writing the browser interface in Python would have meant a slower, less responsive page. Writing the recommender in JavaScript would have meant re-implementing numerical libraries by hand. Splitting the system also gives the architecture diagram in Chapter 5 a genuine reason to exist: the two halves talk to each other over a defined web interface, so each can be replaced without rewriting the other.

5. READY-TO-USE WORDING FOR THE PAPER

The paragraphs below are written in the past tense and in plain academic English, matching the department's requirement. They are a starting point to be edited into the student's own voice — the guidelines require the words to be her own, so they should not be pasted unchanged.

5.1 For Chapter 3 (Methodology) — development tools

The system was developed as a two-tier web application. The client side was implemented in TypeScript 5.6, a superset of JavaScript that adds static typing, and was built with React 18 and Vite 5. Styling was written with Tailwind CSS. The server side was implemented in Python 3.11 using the FastAPI framework, with SQLAlchemy for database access and scikit-learn for the recommendation model. PostgreSQL was used as the database management system in production, with SQLite used for local development. The choice of TypeScript on the client and Python on the server allowed the user interface and the recommendation logic to be developed, tested and modified independently of each other.

5.2 For Chapter 6 (Implementation) — languages and versions

The implementation used two programming languages. TypeScript was used for all client-side code, compiled to JavaScript by Vite before being served to the browser. Python was used for all server-side code, including the recommendation engine. The version of each language and library is given in Table 6.x. TypeScript was selected because its type-checking identifies inconsistencies between the data returned by the server and the data displayed on screen before the application is run. Python was selected because the machine-learning libraries required by the recommendation algorithm are written in Python, allowing the web server and the recommendation model to run within a single application.

5.3 For Chapter 5 (Design) — architecture sentence

The system follows a client–server architecture. The presentation tier is implemented in TypeScript and runs in the user's browser; the application tier is implemented in Python and runs on the server, exposing a documented web interface that the presentation tier calls. The data tier is a PostgreSQL relational database. This separation means the recommendation model can be changed without altering any screen, and a screen can be redesigned without touching the model.

7. POINTS TO CONFIRM WITH THE SUPERVISOR

Four questions are worth settling before the chapter is written.

  • Which chapter should carry the full description — Chapter 3, section 3.7 (development tools), or Chapter 6, section 6.2 (tools used for coding and testing)? The recommendation in this note is Chapter 6, with a one-line cross-reference in Chapter 3.
  • Should CSS and SQL be listed as programming languages, or named separately as a style-sheet language and a query language? Listing them without comment is the usual cause of a lost mark.
  • Does the department want version numbers in the body text or only in a table? The guidelines mention version numbers for Chapter 6, but not the format.
  • Should the libraries be listed in full in Chapter 6, or moved to an appendix with only the main ones named in the chapter? A table of eleven libraries can take most of a page that the chapter limit does not allow.
